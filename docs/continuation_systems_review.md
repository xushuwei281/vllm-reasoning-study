# Continuation systems review

This review covers the verified cloud environment, completed baseline development and frozen execution/accounting code. The live optimizer comparison was in progress when this note was written; it does not report a winner or a completed held-out result. The evidence boundary is the frozen search plan dated 2026-11-03 12:00:05 UTC and the baseline records below. Later campaign and terminal-allocation records remain authoritative for final results.

The [measured environment](../results/continuation/environment.json) identifies one NVIDIA A10G with 24,146,608,128 visible bytes (22.488 GiB), CUDA available, driver 580.178.04 and NCCL 2.27.3. The container is `vllm/vllm-openai:v0.10.2`: Python 3.12.11, vLLM 0.10.2, PyTorch 2.8.0+cu128, CUDA runtime 12.8, Transformers 4.56.1 and huggingface-hub 0.34.4. Linux is x86_64. The collector sees 48 logical host CPUs and 200,454,582,272 host-RAM bytes; these visibility figures are not a statement of the job's CPU/RAM entitlement. The environment's generic Apple unified-memory note does not apply to this CUDA GPU. The cloud environment hash is `b2c034ec0c1ec3ce047810efecc163d64ad8f7b85ab20f90a3ed1d6ef7aa735e`.

The [successful preflight](../results/continuation/preflight.json) reports `ok=true` and no errors. vLLM 0.10.2 needs ordinary `serve --help`; its `--help=all` searches for names containing “all” and therefore omitted valid flags. That failed preflight is preserved separately. The compatibility fix retains the newer Metal runtime's `--help=all` behavior and still rejects missing flags. The installed output and [pinned v0.10.2 parser source](https://github.com/vllm-project/vllm/blob/v0.10.2/vllm/entrypoints/utils.py) support this distinction. The coordinator reports **173 passing full-suite tests** before campaign execution; this is a CPU software-verification result, not a hardware performance result.

The model and tokenizer remain Qwen/Qwen3-1.7B revision `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`, with an 8,192-token context. The [pilot server log](../results/continuation/runs/cloud-baseline-pilot-00/server.log) confirms CUDA, BF16 weights, TP=PP=DP=1, no quantization, Flash Attention, FlashInfer top-k/top-p sampling, chunked prefill and CUDA graphs. It records 3.2152 GiB for model loading, 28.93 seconds for compilation, 131,200 KV-cache token slots and a default 2,048-token scheduler batch. These are that pilot's initialization observations, not guaranteed values for every candidate. “Default” means omitted scheduler batch/sequence limits within the study's common BF16, memory-fraction-0.8, chunked-prefill-on, prefix-cache-off setup; it is not an untouched vLLM invocation.

The [frozen search plan](../results/continuation/search-plan.json) varies scheduler batch limits {512, 1024, 2048} and sequence limits {8, 16, 32, 64}. BF16, TP=1, GPU-memory fraction 0.8, automatic KV dtype and disabled prefix caching are common controls. The thinking template remains enabled. Temperature 0.6, top-p 0.95, top-k 20, min-p 0, presence penalty 1.5, per-question seeds and a 4,096-token cap are frozen across compared configurations. The client uses an open-loop regular arrival trace with uniform jitter; the measured main load is 0.6 requests/second, rather than a Poisson claim inferred from an older workload label. Warmup/ramp requests use the declared 64-token cap and are excluded from measurement quality.

The pilot raw requests, scores, server log and telemetry have been inspected. At review time, the default reference observation was available but its complete raw archive had not yet been synchronized locally. The main default completed 37 requests inside its window and 17 during drain; drain results remain in cohort accuracy but do not increase window goodput. A length-capped HTTP success is not a transport error and is scored unsuccessful when no acceptable final answer is complete. Both observations flag insufficient tail sample size. Their P99 values do not establish a reliable production tail.

Quality goodput and the stored `correct_per_allocated_accelerator_second` field use the measurement window times device count. They must not be read as whole-run efficiency: startup, drain and padding make the actual allocation longer. The client records TTFT, average TPOT, E2E, intended arrivals, dispatch delays and stream chunk gaps. Chunk gaps are transport observations; complete token-level ITL and separate reasoning/final token totals remain unavailable. Pilot telemetry sampled a maximum of six running requests, zero waiting requests and KV utilization 0.05891 (about 5.89%); this describes only the pilot. `nvidia-smi` memory samples measure device usage, not reserved accelerator-seconds.

The original **28,800 accelerator-second ceiling** and 25% validation reserve remain in the single accounting policy. The three Metal pilots retain their 571.171428-second charge and stay outside cloud optimizer training. The [first failed cloud allocation](../results/continuation/cloud-allocations/6ae9c7870e0338d1bb7f1de1.json) failed because the image provides `python3`, not `python`; all 77.502 seconds from creation to terminal state were conservatively charged, including scheduling. It produced no serving result. The replacement [cloud allocation record](../results/continuation/cloud-allocation.json) retains the one-device, four-hour timeout and cost ceiling; its allocation is not free while the server is stopped.

Final accounting must charge the successful job's complete creation-to-terminal interval and subtract already charged overlapping per-trial reservations before appending residual setup, download, optimization, idle and export time. This avoids both omission and double counting. A mid-campaign local ledger copy is not the final budget balance. Nominal 300-second search slots are minimum allocated intervals, with a conservative 445-second admission estimate for the frozen main protocol. The observed default used 300.000130863 seconds: 182.859174772 seconds of server lifecycle, 117.140956091 seconds after shutdown, including 116.735666832 seconds of explicit padding. Its 0.000130863-second slot overshoot is retained. For the planned fixed-compute arms, startup consumes the whole-reservation budget; warmup/ramp and teardown are subtracted before service, then any unused allocation is padded. Actual overshoot remains charged and must qualify any claim of exactly matched compute.

W8A8 was not measured: there is no calibrated quantized checkpoint, matching kernel evidence or independent quality assessment in this continuation. TP>1 and prefill/decode disaggregation were not measured because the allocation contains one GPU. Installed NCCL does not constitute a multi-GPU communication experiment. Ascend/CANN/HCCL were absent and have no measurements. FP16 appears in capability discovery but the frozen comparison is BF16 only. These exclusions keep the result scoped to the actual A10G workload and controls; they do not establish that the excluded methods are intrinsically unsupported or inferior.
